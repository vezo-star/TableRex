The problem

Bookings still run on phones, paper and hope

Every venue that sells time faces the same four headaches.

Double bookings

Two hosts, one table, one awkward evening. Spreadsheets cannot stop two people booking the same slot.

No-shows

An empty table on a full book is lost revenue that cannot be won back later that night.

Phone-only

Guests want to book at 23:00 from the couch, not wait on hold during the dinner rush.

Many locations

Each site runs its own book. Nobody sees the whole business, and every venue sets itself up differently.

Keep this short. Ask the audience which of the four hurts most in their venue; the rest of the deck answers each one.

Taking a booking

Three steps. No clashes.

  • The table is held while you type the details, so nobody can take it from under you.
  • Best table picked automatically, or choose one, including joined tables.
  • Walk-ins in seconds: no name needed, seated straight away.

Online booking

Built for the phone in their pocket

  • Pick a date and party size, then tap a time. Only bookable tables are offered.
  • No account, no password. Name and email are enough.
  • Double taps are safe: a nervous second tap never creates a second booking.
  • Your brand: logo, colour, welcome message and booking terms.
Booking PlatformGuest experience
Each venue controls its own online rules: minimum notice, how far ahead, online party-size range, and which tables are bookable online. Larger groups see the venue's phone number instead.

Deposits

Deposits that make no-shows expensive

Set a fixed amount per booking or per guest, and a time limit for paying. Unpaid bookings release the table automatically.

Booking PlatformGuest experience
If the deposit isn't paid in time, the worker cancels the booking and frees the table without staff doing anything. A payment that arrives too late is flagged in the booking's Payments tab so a manager can refund it. Going live means plugging a real provider into the existing payment interface.

Stay informed

Guests stay informed and in control

  • Automatic emails when a booking is requested, confirmed or cancelled.
  • A private link to view the booking or cancel it until the venue's cutoff.
  • Replies reach the venue: the reply-to address is the venue's own email.
  • Reliable delivery: emails are queued in the same transaction as the booking and retried if the mail server is down.
Booking PlatformGuest experience
The manage link carries a secret token after the # in the address, so it never appears in server logs. Guests can't change the time online; staff do that with Edit or Move.

No double bookings

Impossible, not just unlikely

We fired 100 booking requests at the same table, for the same time, at the same instant.

1
booking created
99
told "just taken"
0
errors or duplicates
  • The database itself refuses overlaps, using an exclusion constraint on table and time.
  • Every create is idempotent: retries and double taps return the original booking.
  • Edits are versioned, so concurrent changes never silently overwrite each other.

100 concurrent requests for one table, from the automated test suite and the load test.

Booking PlatformEngineering
This runs automatically in the test suite against a real PostgreSQL database in a container, and again as a load test against the production-like stack. The application can't get this wrong, because the database won't store two overlapping active allocations for one resource.

Security & privacy

Secure by default, private by design

Tenant isolation

Every query is scoped to the business taken from a server-verified token, never from the browser.

Strong sign-in

PBKDF2-SHA512 password hashing, rotating refresh tokens with reuse detection, and lockouts.

Rate limits

Sign-in, password reset and every public endpoint are throttled against abuse and bots.

Least privilege

The app connects as a restricted database role: data access only, no schema changes.

Full audit trail

Every change records who made it, when, from where, and the before and after values.

Privacy tools

One-click customer anonymisation keeps bookings for reporting but removes personal data.

Hardened web app

Strict Content Security Policy, security headers, and no secrets in source control.

Accessible

Meets WCAG 2.1 AA: 0 automated accessibility violations across 43 views.

Booking PlatformEngineering
Public pages expose only what a guest needs: no internal notes, no customer records. Errors never leak stack traces outside development.

Booking PlatformEngineering
Deliberately boring technology: one API and one background worker sharing the same code, rather than microservices. Side effects such as emails and live updates are written to an outbox in the same database transaction as the booking, so a booking never exists without its notification, or the other way round. If Redis goes down, bookings keep working; only live updates pause, and screens fall back to refreshing every minute.
